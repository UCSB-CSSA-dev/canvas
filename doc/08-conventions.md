# 08 Conventions

Rules for humans and agents writing code in this repo.

## Tooling

- **Package manager**: npm workspaces (`backend`, `frontend`). Run scripts from the root; they fan out with `--workspaces`.
- **Language**: TypeScript everywhere, `strict: true`. No `any` except Convex `v.any()` fields that are documented.
- **Lint**: ESLint (Next.js config in `frontend/`, typescript-eslint in `backend/`). Run `npm run lint` and `npm run typecheck` before committing.
- **Node**: 22 (see `.nvmrc`).

## Project structure

See the tree in the [README](../README.md#repository-structure). Additional rules:

- `frontend/app/` contains routes and layouts only. Keep pages thin; move UI into `frontend/components/<feature>/`.
- `frontend/components/ui/` is generated by shadcn (`npx shadcn add <name>` from `frontend/`). Edit generated components only for theme-level changes.
- `frontend/components/<feature>/` holds feature components: `auth/`, `chat/`, `roster/`, `people/`, `layout/`, `providers/`; later `files/`, `assignments/`, `admin/`, `notifications/`.
- `frontend/lib/` holds client utilities (`api` re-exports, `localized`, `displayName`, `useErrorToast`, `cn`).
- `backend/convex/` holds all backend code. `backend/convex/lib/` holds shared server helpers (permissions, audit, validators, constants).
- Shared constants (limits, consent version, error codes) live in `backend/convex/lib/constants.ts` and are imported by both Convex and the frontend (via `frontend/lib/api.ts`). That file must stay free of server-only imports.
- `backend/convex/_generated/` is committed so the frontend and CI can typecheck without a Convex deployment. Regenerate it with `npm run dev:backend` after changing functions or the schema.

## Naming

| Thing | Convention | Example |
| --- | --- | --- |
| React components | PascalCase file and export | `MessageList.tsx` |
| Hooks | `use` prefix, camelCase | `useViewer.ts` |
| Route folders | kebab-case, no dynamic segments | `frontend/app/(app)/admin/audit` |
| Convex files | camelCase nouns, one per domain | `convex/messages.ts` |
| Convex functions | verb or verbNoun | `messages.send`, `channels.listMine` |
| Tables | camelCase plural | `assignmentSubmissions` |
| Indexes | `by_field[_field]` | `by_channel_user` |
| i18n keys | `feature.area.meaning` | `files.upload.tooLarge` |
| Audit actions | `domain.verb` | `user.approve`, `oversight.channel.open` |

## Convex patterns

- Every public function declares `args` with validators and, when practical, `returns`.
- First line of every public handler (except onboarding):

```ts
const viewer = await requireApproved(ctx);
```

- Use indexes with `.withIndex(...)`. Avoid `.filter()` on large tables; add an index instead.
- Use `.paginate()` for lists that can grow (messages, notifications, audit logs, files in big folders).
- Side effects (notifications, email) go through `ctx.scheduler.runAfter(0, internal....)` so the user-facing mutation stays fast and transactional.
- Actions (`"use node"` only if a Node API is needed) do external I/O such as calling Apps Script. Actions write results back through internal mutations.
- Throw `ConvexError({ code, message? })` with the codes from [02-roles-and-permissions.md](02-roles-and-permissions.md#permission-helpers-convexlibpermissionsts).
- Derive access from source-of-truth rows (e.g. department channel access from `departmentMemberships`) instead of copying it into other tables that could drift.

## Frontend patterns

- Client components call Convex hooks directly. Server components are used only for layouts that render no translated text (the export is static and the locale is client-side).
- Forms: controlled React state for the current small forms, with `maxLength` and submit checks taken from the shared `LIMITS`. Introduce `react-hook-form` + `zod` when a form grows past a handful of fields.
- Optimistic updates for toggling reactions and similar (`useMutation(...).withOptimisticUpdate`) from Stage 2. The Stage 1 composer clears the input immediately and restores it if sending fails.
- Text inputs that send on Enter must ignore Enter while an IME is composing (`event.nativeEvent.isComposing`), otherwise picking a Chinese candidate sends the message.
- Toasts (`sonner`) for success and error feedback; errors are translated from `ConvexError` codes.
- Accessibility: use semantic elements and shadcn's accessible primitives; every icon-only button has an `aria-label` from i18n.
- Styling: Tailwind utility classes and design tokens only. No inline hex colors.

## Git and commits

- Branches: `feat/<area>-<short-name>`, `fix/<area>-<short-name>`, `docs/<topic>`.
- Commit messages: Conventional Commits, in English. Examples: `feat(chat): add message reactions`, `fix(files): block executable uploads`, `docs(roles): clarify lead oversight`.
- One logical change per pull request. Include doc updates in the same PR when behavior changes.

## Testing

| Layer | Tool | What to cover |
| --- | --- | --- |
| Convex functions | `convex-test` + Vitest | **Permission rules first**: for each function, test presidium, lead, member, non-member, pending, and deactivated callers |
| Pure helpers | Vitest | Formatting, `localized`, permission helper logic |
| UI components | Vitest + Testing Library | Critical components: composer, upload, assignment form |
| End-to-end | Playwright (Stage 5) | Sign-in gate, send a message, upload a file, submit an assignment |
| i18n | `frontend/scripts/check-i18n.mjs` (`npm run check:i18n`) | `zh.json` and `en.json` have identical keys |

Backend tests live in `backend/tests/` and use the helpers in `backend/tests/helpers.ts` (`setup`, `signInUser`, `bootstrapAdmin`, `addMember`, ...).

Minimum before merging a feature: CI is green (lint, typecheck, tests, i18n check, static build), and the feature's permission tests exist and pass.

## Definition of done

- [ ] Behavior matches the feature spec in `doc/features/`, including acceptance criteria.
- [ ] Server-side permission checks and tests for every new function.
- [ ] All strings translated in `zh` and `en`.
- [ ] Works at mobile width (375px) and desktop.
- [ ] Docs updated if behavior, schema, routes, or permissions changed.
